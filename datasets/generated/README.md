# Generated carriers (`corpus_v1`)

151 clean designs with generated testbenches are retained for provenance; 148 are eligible for the closed red–blue loop (`r3e/loop/`). They contain no bugs: bugs are made by Red during a run.

| Source | Retained | Eligible | Upstream commit | License |
|---|---:|---:|---|---|
| VerilogEval v2 (`NVlabs/verilog-eval`) | 113 | 110 | `c498220d0a52248f8e3fdffe279075215bde2da6` | MIT (`licenses/VerilogEval-MIT.txt`) |
| RTLLM v2 (`hkust-zhiyao/RTLLM`) | 38 | 38 | `51ed553d0ffd32797a1a0a13e051656bf302c81f` | MIT (`licenses/RTLLM-MIT.txt`) |

`Prob062_bugs_mux2`, `Prob123_bugs_addsubz`, and `Prob132_always_if2` are marked
`eligible: false` with `ineligible_reason: spec_task_mismatch: ...`. Their upstream
prompts describe a particular faulty implementation to repair, which can mislead
Blue when Red instead mutates the clean carrier. The loader excludes these rows
before constructing the experiment pool; re-extraction preserves this exclusion.
Their files and original descriptions remain available for audit.

Each design directory holds:
- `clean.sv`: the upstream reference design (only the top module may be renamed);
- `spec.txt`: the upstream problem description, with any HDL examples transcribed into prose as described below;
- `tb_visible.v`: a random-stimulus testbench (seed 11, 64 cycles). It writes the outputs per cycle to `trace_visible.txt` and the applied inputs to `stimulus_visible.txt`.
  - The first column of both files is the simulation time of the sample (`$time`). Until 2026-10-04 it was the cycle index.
  - The time change left every logged value identical (checked for all 302 traces); only the testbench file hashes changed.
  - The time lets the runner align a design's register dump with the trace (`r3e/knowledge/register_trace.py`).
- `tb_hidden.v`: a random-stimulus testbench (seed 97, 160 cycles), outputs only.

Expected outputs are not stored: the runner obtains them by simulating `clean.sv`.

A design is admitted by `r3e/loop/carriers.py::build_carrier` only if:
- its ports are readable;
- the clean design passes both testbenches deterministically;
- no output is X/Z or constant;
- it offers at least three mutation sites.

`carriers.jsonl` records, per carrier: its id, cluster, ports, clock and reset, the repository-relative paths and SHA-256 of each file, and the upstream source.

## Specifications

All 151 rows include a `spec` path and a corresponding entry in `files`.
`spec_source` records the upstream description path, pinned commit, SHA-256 of
the original bytes, and any adaptations. The generated-carrier loader reads
the text into `Carrier.spec`; Blue receives it as `specification`, including
for bugs subsequently generated by Red. Original task openings are retained.
Rows from other corpora without a specification remain supported.

To extract the descriptions again from local upstream Git repositories:

```sh
python scripts/extract_generated_specs.py \
  --verilog-eval-root /path/to/verilog-eval \
  --rtllm-root /path/to/RTLLM
```

The extractor reads the exact commits in the manifest using Git, rather than
the current working copies. It takes VerilogEval descriptions from
`dataset_spec-to-rtl/<problem>_prompt.txt`, and RTLLM descriptions from the
`design_description.txt` beside the source RTL. It does not derive requirements
from the reference implementation or regenerate RTL/testbenches. It validates
all descriptions and existing file hashes before writing. Repeated runs are
idempotent; replacing a different existing spec requires `--overwrite`.

Most descriptions are copied byte for byte. Twenty-one RTLLM descriptions
receive an appended note mapping the original module name to the corpus's
actual top-level name. Six VerilogEval prompts contain HDL requiring explicitly
reviewed, source-hash-guarded prose adaptations:

| Problem | Adaptation |
|---|---|
| `Prob043_vector5` | Express the pairwise comparison ordering in words. |
| `Prob062_bugs_mux2` | Describe the supplied buggy mux interface and expression in words. |
| `Prob078_dualedge` | Describe the prohibited dual-edge sensitivity list in words. |
| `Prob104_mt2015_muxdff` | Describe the parent module's simultaneous state updates in words. |
| `Prob123_bugs_addsubz` | Describe the supplied buggy arithmetic and zero-flag example in words. |
| `Prob132_always_if2` | Describe the supplied buggy conditional assignments in words. |

Faulty examples are explicitly labeled as such. Surrounding source prose,
including the incongruous adder-subtractor heading in `Prob132_always_if2`, is
preserved. These adaptations do not silently add a corrected implementation;
providing the original specification does not certify it as unambiguous or
consistent with every upstream reference. Unknown HDL fails extraction for
review. The default local report, `artifacts/generated_specs/extraction.json`,
records exact replaced spans, their original text and replacement prose.

The intended repair task for these carriers is specification + buggy RTL +
visible test evidence. This supplies the problem's constants and functional
requirements even when Red mutates them.

RTLLM's original descriptions sometimes explain implementation steps in detail.
They are retained faithfully; Part A results should report VerilogEval and RTLLM
hit rates separately because the available specification detail differs by source.
